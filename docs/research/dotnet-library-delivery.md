# How .NET brings a library, its analyzers and a template into a game

- **Question:** How can a .NET 10 game receive a library, the Roslyn analyzers and source generators that come with it, and a starting project, so that the game builds without Playstead or a package registry, leaves the library out of its release builds, and changes the library only when the person accepts ([#83][ticket])? The answer feeds **How the Playstead library reaches a game, and its versions** (#90).
- **Date:** 2026-10-17. All sources were accessed on this date.
- **Outcome:** NuGet packages, project SDKs and source can all bring the library, but they differ on release builds. NuGet settles package references when it restores, and its documentation says a reference's condition may use only `TargetFramework`. In local checks a `$(Configuration)` condition held when restore and build ran together, but the library reached Release output after a plain restore followed by a build with `--no-restore`. Conditions that MSBuild evaluates during the build held every time, though a conditioned project's own NuGet dependencies still leaked. Analyzers and generators come from a project reference with `OutputItemType="Analyzer"`; they run in every configuration and add nothing to the output. On SDK 10.0.103, `dotnet watch` applied Hot Reload only in the `Debug` configuration. A recommendation; the founder decides: copy the library into the game as source with no NuGet dependencies, leave it out of Release with conditions evaluated during the build, keep its analyzers and generators in a `netstandard2.0` project referenced in every configuration, run the preview in `Debug`, and apply upgrades as three-way merges against the version the game last accepted.
- **Versions:** .NET 10.0.13 (2026-10-13), whose current SDKs are 10.0.402 and 10.0.113 ([release metadata][dotnet-releases]). MonoGame 3.8.6 (2026-10-07, [release][mg-release]), built from commit `c610a52`, with its templates from `MonoGame.Templates` at commit `90600c8`. Local checks ran on SDK 10.0.103 (runtime 10.0.3, NuGet 7.0.2, C# compiler 5.0.0) and Apple Git 2.50.1.
- **Local evidence:** small projects written for this note on a macOS (Apple silicon) computer, in a throwaway folder under `/tmp`, with NuGet's caches, the CLI's home folder and the template store redirected into it. MonoGame's 3.8.6 packages were downloaded from nuget.org and read, not run. These results are marked **Observed**.

Labels: **Documented** (official documentation, repositories, packages or source code), **Observed** (the local checks), **Inference** (reasoning, not a source) and **Unconfirmed** (not established).

## A package from a registry

- **Restore (Documented).** NuGet looks first in the global packages folder (`~/.nuget/packages`) for the exact ID and version, then in local folder sources, then over HTTP ([global packages][nuget-global-folders], [install process][nuget-install-process]). A floating version, or a range without a minimum, makes it ask every source. "In PackageReference projects, all sources need to be available for all restores" ([PackageReference][nuget-packagereference]).
- **Offline (Observed).** With nuget.org unreachable, an exact version already in the global packages folder restored, after about 6 s and an `NU1900` warning from NuGet Audit. A floating `4.14.*` failed with `NU1301`. Audit is on by default and covers transitive packages for `net10.0` projects ([audit][nuget-audit]). Under `TreatWarningsAsErrors`, `NU1900` would fail an offline build (Inference).
- **Unlisted and deleted versions (Documented).** nuget.org deletes packages only in exceptional cases, such as copyright infringement or harmful content. An unlisted version still restores by its exact version, and a floating version can still pick it ([deleting packages][nuget-deleting]).
- **GitHub Packages (Documented).** "You need an access token to publish, install, and delete private, internal, and public packages", and only a personal access token (classic) works outside GitHub Actions ([GitHub Packages][gh-packages-nuget]). Everyone building a game would need one.
- **Lock files (Documented).** `RestorePackagesWithLockFile` writes `packages.lock.json`, which also records each package's `contentHash` (**Observed**). `--locked-mode` fails when the project's dependencies no longer match it ([PackageReference][nuget-packagereference]). Microsoft advises `rollForward: disable` in `global.json` with lock files, because the SDK's implicit package references change with its version ([global.json][global-json], [PackageReference][nuget-packagereference]).
- **Central Package Management (Documented).** `Directory.Packages.props` holds every `PackageVersion`. A `GlobalPackageReference` adds a package to every project with `PrivateAssets="All"` and without compile assets, for analyzers and build tools. With more than one source configured, restore warns `NU1507` unless package source mapping is set ([CPM][nuget-cpm]).
- **Development dependencies (Documented).** A package marked `developmentDependency` is never passed on as a dependency. Tools such as `dotnet add package` then write `PrivateAssets="all"` and leave out compile assets; a hand-written reference is an ordinary one ([PackageReference][nuget-packagereference], [spec][nuget-devdep]). **Observed:** `dotnet add package` wrote exactly that for a lab analyzer package.

## A package kept in the game's repository

- **Folder feed (Documented).** A folder of `.nupkg` files, flat or in NuGet's hierarchy, is a package source, and `nuget.config` can name it by a relative path ([local feeds][nuget-local-feeds]). **Observed:** a game whose `nuget.config` cleared every source and added `packages/` restored and built with no network.
- **Same version, new contents (Observed).** A package rebuilt with new contents under the same version left the game on the old contents. That survived `dotnet restore --force --no-http-cache` and a full rebuild, until that version's folder was deleted from the global packages folder. NuGet reuses an extracted copy by ID and version ([global packages][nuget-global-folders]), and skips package source mapping when it does ([source mapping][nuget-source-mapping]). Every change to the library therefore needs a new version number, and two games carrying different contents under one version would share whichever copy was extracted first (Inference).
- **Lock file and changed contents (Observed).** With a lock file, a computer that still had the old copy restored without complaint. One without it failed with `NU1403: Package content hash validation failed for Playstead.Dev.0.1.0. The package is different than the last restore.`, in locked and normal mode alike.
- **Size in Git (Documented, Inference).** A package is "a single ZIP file" ([NuGet][nuget-what-is]), so Git stores every committed version whole; Microsoft notes that package binaries in source control waste space ([NuGet][nuget-what-is]). The lab's analyzer and runtime packages were 7 KB and 4 KB (**Observed**). Vendoring MonoGame as well would be heavy: `dotnet-mgcb` 3.8.6 alone is 209 MB (**Observed**).
- **MonoGame still comes from nuget.org (Inference).** Unless MonoGame's packages are already in the global packages folder or vendored too, a fresh clone still needs nuget.org; a folder feed frees only the library from a registry.

## Source in the game's repository

- **Analyzers and generators from a project (Documented).** A `ProjectReference` with `OutputItemType="Analyzer" ReferenceOutputAssembly="false"` turns the referenced project's output into an `Analyzer` item and otherwise only makes it build first ([MSBuild items][msbuild-items]). Microsoft's generator sample uses this, imports by hand the props a package would bring, and adds generation-time dependencies with a `GetDependencyTargetPaths` target ([sample][roslyn-sdk-sample], [generator project][roslyn-sdk-sample-gen]). Analyzers and generators should target `netstandard2.0` ([RS1041][rs1041]).
- **In the lab (Observed).** A determinism analyzer and a generator in one `netstandard2.0` project ran in Debug and in Release, and nothing of them reached the output folder. An edit to the analyzer took effect on the next `dotnet build`, with the compiler server already running.
- **Build time (Observed).** On tiny lab projects with warm build servers, the source form took 0.76 s from clean, 0.60 s with no change and 0.62 s after a game edit; the package form took 0.60, 0.46 and 0.48 s. A real library's own compile time is paid only when it changes (Inference).
- **The analyzer project's packages (Observed).** It restores `Microsoft.CodeAnalysis.CSharp` (17 MB at 4.14.0) and `Microsoft.CodeAnalysis.Common` (7 MB) from nuget.org on a computer that lacks them.
- **Updates to an edited copy (Documented).** `git subtree` keeps the library as ordinary files. Its `merge` and `pull` bring in a new version: "As with normal 'git merge', this doesn't remove your own local changes", conflicts are resolved "in the usual ways", and `--squash` makes one commit per update ([git-subtree][git-subtree]). It ships in Git's `contrib` folder; Apple Git 2.50.1 includes it (**Observed**), other distributions are **Unconfirmed**. `git merge-file` merges two sets of changes to one base file ([merge-file][git-merge-file]), and `git apply --3way` falls back to a three-way merge when the patch names blobs the repository holds ([apply][git-apply]). Each needs the version the game last accepted as its base (Inference).

## Other mechanisms in use

- **MSBuild project SDKs (Documented).** `Sdk="Name/version"`, an `<Sdk>` element or an `Import` brings in an SDK's `Sdk.props` and `Sdk.targets`. NuGet's resolver finds the SDK in the configured feeds, and only when a version is given; `global.json` can hold the version under `msbuild-sdks` ([project SDKs][msbuild-sdk]). The resolver accepts only an exact version and looks in the global packages folder first ([resolver source][nuget-sdk-resolver]). **Observed:** a lab SDK from a folder feed added source and an analyzer, and its `Sdk.targets` left the source out of Release even after a Debug restore and a Release build with `--no-restore`. Its files live in the global packages folder, not in the game. Without the package the build stops with `MSB4236`.
- **Git submodules (Documented).** The parent repository records a commit. A clone gets an empty folder until `git submodule update` fetches from the URL in `.gitmodules`, and work inside a submodule starts on a detached HEAD and must be pushed to the submodule's own repository ([submodules][git-submodules]). A fresh clone therefore needs that repository reachable (Inference).
- **Source-only packages (Observed).** `contentFiles` with `buildAction="Compile"` compile a package's `.cs` files into the game. They compiled from the global packages folder, outside the game, and a `$(Configuration)` condition on the reference let them into Release after a Debug restore, as with any package.
- **Local tools (Documented).** `.config/dotnet-tools.json` pins each tool's version, and `dotnet tool restore` installs the tools into the global packages folder ([tools][dotnet-tools], [tool install][dotnet-tool-install]). `--allow-roll-forward` (.NET 9 SDK) lets a tool run on a newer runtime.
- **MonoGame's content builders (Documented).** `MonoGame.Content.Builder.Task` 3.8.6 runs `dotnet tool restore` before it collects package references, then `dotnet mgcb` on each `.mgcb` file before compiling ([package][mg-task-pkg]). `dotnet-mgcb` 3.8.6 targets `net8.0` with `rollForward: Major` ([package][mg-mgcb-pkg]). From 3.8.6 MonoGame's documentation prefers the Content Builder, a console project in the solution with "no `dotnet-tools.json`, no editor to install, and no `.mgcb` file to keep in sync". An imported `BuildContent.targets` builds and runs it before compiling, and it needs the .NET 10 SDK ([Content Builder][mg-content-builder]).

## Leaving it out of release builds

- **Conditions on package references (Documented, Observed).** NuGet's documentation says conditions "can use any MSBuild variable … However, at present, only the `TargetFramework` variable is supported" ([PackageReference][nuget-packagereference]). **Observed:** with `Condition="'$(Configuration)' != 'Release'"`, `dotnet build -c Release` and `dotnet publish` restored for Release and left the library out. A plain `dotnet restore` followed by `dotnet build -c Release --no-restore`, or by `dotnet publish -c Release --no-restore`, shipped `Playstead.Dev.dll`. A Debug build with `--no-restore` after a Release restore failed with `CS0103`. One `obj/project.assets.json` serves every configuration, so each switch rewrites it, and NuGet does not guard against two restores of the same project at once ([global packages][nuget-global-folders]).
- **Conditions evaluated during the build (Observed).** A `Compile Remove="Playstead/**"` for Release, and a `ProjectReference` conditioned on the configuration, kept the library out whatever the order of restore and build. The conditioned project's own NuGet dependencies still reached Release output through the assets file.
- **Compilation symbols (Documented).** The SDK adds the configuration's name in capitals as a symbol, such as `DEBUG`, `RELEASE` or `DEVELOPMENT`, unless `DisableImplicitConfigurationDefines` is set ([C# targets][sdk-csharp-targets]). `[Conditional]` on an attribute class leaves its uses out of the metadata when the symbol is not defined ([C# attributes][conditional]).
- **What game code can name in every build (Observed).** A generator emitted a marker attribute marked `[Conditional("PLAYSTEAD_DEV")]` in every configuration, with Roslyn's `EmbeddedAttribute`, as the generator cookbook advises ([cookbook][roslyn-cookbook]). Game code used it without `#if`. The Release assembly kept the two small internal attribute types, but no use of them and no reference to the library. The same generator emitted its list of capabilities only when `PLAYSTEAD_DEV` was defined. Code that names a library type outside `#if` does not compile when the library is absent (**Observed**, `CS0103`). An interface the game implements in every build must therefore exist in every build and would ship. Instead, a generator can add the implementation in development builds only, as it did for the capability list, or the game can keep development-only members in partial-class files that Release builds remove (Inference).
- **Trimming (Documented).** Trimming removes unused code only from trimmed, self-contained publishes. A `FeatureSwitchDefinition` property, switched off with `RuntimeHostConfigurationOption … Trim="true"`, lets it remove the code it guards ([feature switch][feature-switch], [trimming][trimming-libs]). The library stays referenced, and untrimmed builds keep it (Inference).
- **A third configuration (Documented, Observed).** The SDK sets `Optimize=false` and debug symbols for `Debug` and `Optimize=true` for `Release`, and nothing for other names ([SDK props][sdk-props]). A `Development` configuration got no `Optimize` value, so it compiled unoptimised, and it defined `DEVELOPMENT`; an optimised development build must set `Optimize=true` itself (**Observed**).
- **Hot Reload and configurations (Observed).** With `dotnet watch` on SDK 10.0.103, a method edit applied in about 0.5 s in `Debug`. In `Release`, and in `Development` with or without debug symbols, it printed "No C# changes to apply", and the game kept its old code. With a stale `Debug` build present, `-c Development` reported "Hot reload succeeded" while the update targeted the `Debug` build's module ID, not the module running. `Debug` with `Optimize=true` was refused: "The assembly can not be edited or changed".
- **Why (Documented).** Microsoft's Visual Studio Hot Reload page says "Release or custom build configurations aren't supported" and lists trimming among unsupported settings ([Hot Reload][vs-hot-reload]). The 10.0.1xx `dotnet watch` loads its Hot Reload workspace without the command line's properties ([1xx source][watch-workspace-1xx]); 10.0.4xx builds it from its own project graph with them ([4xx source][watch-workspace-4xx], [graph][watch-graph-4xx]), so a current SDK may behave differently (**Unconfirmed**). Changing compilation symbols needs a restart ([Roslyn][roslyn-project-settings]). Methods already running keep their old code, and the next call runs the new code ([MetadataUpdater][metadata-updater]).
- **Hot Reload and the library (Observed).** Edits to the library's runtime source applied in place. A game edit that changed a generated static field's initialiser restarted the game (`ENC0118`), as `--non-interactive` does for rude edits ([dotnet watch][dotnet-watch]). An edit to the generator itself was reported as succeeded and had no effect on the running game.

## Templates

- **Packaging and installing (Documented).** A template package is a `.nupkg` with `PackageType` `Template` and templates under `content/`; folders starting with a dot, such as `.template.config`, need `NoDefaultExcludes` ([template package][template-package]). `dotnet new install` takes a NuGet ID with `@version`, a `.nupkg` path or a folder; a path already installed is not reinstalled, and installed packages serve later SDKs ([install][dotnet-new-install]). `template.json` offers name substitution, symbols, conditional files, post actions and constraints ([reference][template-json]).
- **In the lab (Observed).** A template installed from a folder was read in place: an edit appeared in the next `dotnet new` without reinstalling. Installing version 0.2.0 from its `.nupkg` path kept 0.1.0 installed beside it, and `dotnet new update --check-only` failed for both: "the package is not available in configured NuGet feeds". `--debug:custom-hive <folder>` recorded the installs in that folder instead of the user's own store; Microsoft's documentation does not cover it (**Unconfirmed** as a supported option).
- **MonoGame's templates (Observed, Documented).** `MonoGame.Templates.CSharp` 3.8.6 is 27.8 MB with 16 templates, among them `mgdesktopgl`, `mgblankmgcbstartkit` and `mgcb` ([package][mg-templates-pkg], [source][mg-templates-repo]). `mgdesktopgl` targets `net9.0` with `RollForward=Major` and `TieredCompilation=false`, floats `MonoGame.Framework.DesktopGL` and `MonoGame.Content.Builder.Task` at `3.8.*`, and pins the `dotnet-mgcb` tools at 3.8.6. The Content Builder start kits pin 3.8.5 and float several `MonoGame.Tool.*` and `MonoGame.Library.*` packages with four-part wildcards. With only the .NET 10 SDK installed, a `net9.0` project downloads the 9.0 targeting pack from nuget.org when it restores, and with `RollForward=Major` it runs on .NET 10 (**Observed**).
- **What writing the files itself would lose (Inference).** Discovery in `dotnet new list` and in IDEs' new-project dialogs, a way to create the same game without Playstead, and the template engine's substitution, conditions and post actions. Nothing about building or upgrading: templates only create, and MonoGame says "Updating the templates will not affect existing projects" ([updating][mg-updating]).

## Versions that move apart

- **MonoGame (Documented, Observed).** The framework, the content task and the `dotnet-mgcb` tools carry separate versions in two files, and MonoGame's update guide has both edited by hand ([updating][mg-updating]). The task runs whichever `mgcb` the manifest pins, with no check against the framework ([package][mg-task-pkg]), and `ContentManager` checks only the XNB format version, 4 or 5 ([source][mg-contentmanager]). The 3.8.6 template package writes 3.8.5, 3.8.6 and `3.8.*` in different templates (**Observed**). Since 3.8.2 the tool is local, "allowing different projects to use different versions" ([what's new][mg-whats-new]).
- **Analyzers and the compiler (Documented, Observed).** `CS9057` says an analyzer "cannot be used because it references version … of the compiler, which is newer than the currently running version" ([diagnostics][cs9057]). **Observed:** an analyzer built against `Microsoft.CodeAnalysis` 5.9.0 was skipped by SDK 10.0.103, whose compiler is 5.0.0, with only that warning; the build succeeded without the determinism check. An analyzer meant for every .NET 10 SDK must reference a `Microsoft.CodeAnalysis` no newer than the oldest SDK's compiler, and treating `CS9057` as an error would make a skipped check fail the build (Inference).
- **The SDK and tools (Documented).** `global.json` pins the SDK with a roll-forward policy, and .NET 10 adds `paths` and `errorMessage` ([global.json][global-json]). The .NET 9 SDK detects a "torn SDK", where Visual Studio's MSBuild and the SDK differ, and downloads a matching compiler package ([.NET 9 SDK][dotnet9-sdk]). A tool rolls forward to a newer runtime only when its runtime configuration or `--allow-roll-forward` allows it ([tool install][dotnet-tool-install]).

## Comparison

| Delivery                              | Builds without Playstead or a registry               | Left out of release builds                     | Analyzers and generators            | Upgrades only when accepted                   | The agent can read and change it                            | Hot Reload, in `Debug` only                 |
| ------------------------------------- | ---------------------------------------------------- | ---------------------------------------------- | ----------------------------------- | --------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------- |
| Package from nuget.org                | Only once cached; GitHub Packages also needs a token | Only if restore uses the build's configuration | Yes, in `analyzers/`                | Yes, with exact versions                      | Reads compiled code; cannot change it in the game           | Game code only                              |
| Package in a folder feed in the game  | Yes, for the library                                 | Only if restore uses the build's configuration | Yes, in `analyzers/`                | Yes, if every change gets a new version       | Reads compiled code; cannot change it in the game           | Game code only                              |
| Source project referenced by the game | Yes, once the analyzer's Roslyn packages are cached  | Yes; its own NuGet dependencies can leak       | Yes, built from source              | Yes; merging edits needs the accepted version | Yes                                                         | Library yes; generator edits need a restart |
| Source inside the game's project      | Yes                                                  | Yes, with `Compile Remove`                     | Through a separate analyzer project | Yes; merging edits needs the accepted version | Yes                                                         | Yes, as game code                           |
| MSBuild project SDK in a folder feed  | Yes, for the library                                 | Yes, in `Sdk.targets`                          | Yes, as `Analyzer` items            | Yes, exact versions only                      | Reads it in the package cache; cannot change it in the game | Game code only                              |
| Source-only package                   | As its feed                                          | Only if restore uses the build's configuration | Only with an `analyzers/` folder    | Yes, with exact versions                      | Reads it in the package cache; cannot change it in the game | **Unconfirmed**                             |
| Git submodule                         | Needs the library's repository reachable             | As source                                      | As source                           | Yes, by commit                                | Yes, but changes go to the library's own repository         | As source                                   |

## Open points

- Whether `dotnet watch` on SDK 10.0.4xx applies Hot Reload in a custom configuration; the lab should be rerun on the current SDK.
- Whether a separate restore output per configuration (`MSBuildProjectExtensionsPath`), or NuGet 7.6's target-framework aliases for one framework (SDK 10.0.300 and later, [PackageReference][nuget-packagereference]), makes package conditions safe. Neither was tested.
- How Visual Studio, Rider and VS Code restore a project with configuration conditions, and whether they offer a custom configuration.
- Whether `git subtree` ships with Git for Windows and in the Linux distributions .NET 10 supports.
- Whether content built by one 3.8.x content builder loads in a different 3.8.x framework.
- Whether `--debug:custom-hive` stays available in later SDKs.
